# 项目讲解稿

## 30 秒版本

“我做的是 GEA，一个 AI 用户研究和通用智能体平台。用户输入研究目标后，系统先做澄清和计划确认，再由 worker 执行联网研究、Persona 生成、合成访谈和报告生成。技术上我比较关注工程闭环：任务和运行状态落 PostgreSQL，支持依赖、租约、幂等、checkpoint、重试、取消和 SSE 进度；报告中的结论要能回到来源和证据。平台还提供 Universal Agent 和版本化 Skill，外部代码放在独立的 Docker/Podman 沙箱里执行。”

## 1 分钟版本

“GEA 解决的是用户研究周期长、资料来源杂、结果难复核的问题。前端是 Next.js App Router，后端是 TypeScript 领域服务和 Route Handler，数据用 PostgreSQL/Supabase，本地恢复场景有 PGlite。创建研究时，系统先根据 Brief 识别问题类型和证据需求，生成计划，用户确认后进入 worker 队列。worker 按 `study_tasks` 的依赖执行研究、Persona、访谈和报告任务，每个调用都写入事件、artifact、Skill 版本和 Context 快照。报告不是直接让模型写完就结束，而是先生成草稿，再由独立 judge 检查证据覆盖、引用和可读性，失败时只基于已有证据定向修订。Universal Agent 只能提出结构化动作，Harness 会再次校验权限、参数、预算和动态任务额度。长任务进度通过 SSE 推给页面，断线可以用游标恢复。”

## 3 分钟版本

“项目可以分成产品层、执行层和治理层。

产品层提供账户、工作区、研究项目、Persona 库、访谈项目、报告和 Universal Agent。用户创建研究后可以补充研究焦点、选择方案并确认计划；也可以通过公共邀请进行访谈，实时访谈 turn 会持久化。

执行层的核心是 Postgres-backed Harness。研究计划会落成 `study_tasks`，任务带 `depends_on`、状态和输入快照。独立 worker 从 job queue 领取任务并写 lease，完成后记录 artifact 和事件。任务调用使用幂等键，worker 中断后会把 lease 过期任务恢复；网络超时、限流和上游错误进入可重试路径，参数或权限问题进入终态，需要补充信息时进入 `waiting_input`。任务结果和运行状态是数据库权威快照，SSE 只是增量通知。

治理层解决模型不可靠和数据不可追溯的问题。模型输出先经过结构化 schema，再映射为 `call_tool`、`replan`、`ask_user` 或 `finish` 等有限动作。模型不能直接写 SQL、提升权限或跳过研究确认；动态任务只能经过 Plan Mutation Service 写入 ledger。每个工具调用会锁定 Skill 版本、能力 grant、Context retrieval snapshot 和预算。报告采用 evidence catalog/evidence graph，区分官方或授权材料、公开网页、模型推断和合成内容。报告生成后有 judge 和 finalize gate，避免把没有证据支持的推断写成事实。

对于用户上传或工作区发布的 Skill，Next.js 只负责解析 manifest、检查 grant、版本和请求 hash，实际 JavaScript/Python 执行交给独立 Sandbox Runner。Runner 使用临时工作区和新容器，非 root、只读 rootfs、关闭网络、限制 CPU/内存/PID/超时/输出，并在退出时清理容器。这样把高风险执行面从 Web 进程隔离出来。这个项目的关键不是某一个模型 API，而是把模型能力放进一个可恢复、可解释、可审计的系统里。”

## 被问“最难的地方”时

“最难的不是把模型接通，而是让失败可恢复、结果可解释。长任务可能遇到 worker 重启、Provider 超时、重复投递和用户中途补充信息，所以我把每个任务的状态、输入 hash、lease、重试分类和 checkpoint 都持久化。另一个难点是模型会输出不符合协议的内容，因此模型只能提出动作，服务端要做 schema 校验和 policy 二次校验。最后，研究结论需要证据边界，我把来源快照、引用、证据关系和报告 gate 作为一等数据，而不是把它们拼在最终 Markdown 后面。”
