# 面试问题与回答

下面的回答按“先给结论，再给实现，再讲边界”的方式写，尽量直接用口语回答。

## A. 项目理解

### 1. 这个项目解决什么问题？

“它把用户研究从一次性问模型，变成一条可追踪的执行链。用户给出研究目标后，系统先澄清和生成计划，再采集来源、生成或复用 Persona、进行合成访谈、整理证据，最后生成和评审报告。每一步都有状态、输入、输出和来源，失败可以重试或等待用户补充，用户刷新页面也能继续看到真实进度。”

### 2. 你负责的核心难点是什么？

“核心难点是可靠执行和可解释性。我把长任务落到数据库任务 ledger，用 worker lease、幂等键、checkpoint 和错误分类解决重启、重复投递和上游失败；又把模型输出收敛成结构化动作，由 Harness 二次校验权限、预算、依赖和 Skill 版本；报告侧把引用和证据做成独立数据，避免最后只剩一段无法核查的文本。”

### 3. 一次研究从哪里开始，到哪里结束？

“从研究 Brief 开始，经过澄清、计划生成和用户确认，创建一个 study run 并把任务写入队列。worker 执行公开网页研究、Persona、访谈、验证和报告任务，结果写入 artifact、evidence 和事件。报告草稿还要经过 judge；通过后 finalize，不通过就基于已有证据定向修订。最终 run 只有在必需任务、证据和报告 gate 都满足时才算 completed。”

### 4. 为什么不直接调用一个 Agent 框架？

“因为这个项目已经有 PostgreSQL 任务状态、租约、重试、checkpoint、waiting-input 和审计。如果再引入一个自带 session 和 tracing 的 runtime，就要维护两套 source of truth。现在采用 Responses API 加自有 Agent Controller：模型负责提出下一步，Harness 负责执行和治理。这样保留已有可靠性，同时逐步增加动态决策。”

### 5. 这个项目算不算完全自主 Agent？

“不能这么说。Universal Agent 有模型决策循环；研究侧默认仍以确定性 DAG 和硬性报告门槛为主，Agent Controller 可以在受控范围提出工具调用和动态任务。`shadow` 只观察不改变执行，`active` 还要通过失败率、拒绝率、工具/模板匹配率和报告 gate 的 rollout 条件。”

## B. 后端和异步执行

### 6. 为什么要独立 worker？

“研究、访谈和 Agent 都可能运行几十秒甚至更久，不适合绑在 HTTP 请求生命周期里。API 只负责校验、创建 run 和 enqueue；worker 独立领取 job、执行工具并写状态。这样可以单独扩容 worker，也能通过 lease 和恢复处理进程重启。”

### 7. worker 如何避免两个实例重复执行？

“领取 job 时在事务里锁定可执行记录并写入 lease owner 和过期时间，其他 worker 看不到有效 lease 的任务。执行过程中定期续租；如果实例宕机，lease 到期后任务才可被接管。真正落库时还会依赖幂等键和唯一约束，避免即使发生重复领取也重复生成 artifact。”

### 8. 幂等键具体解决什么？

“同一个 run 的同一个 task 可能因为网络重试被提交多次。我们为 invocation 使用稳定 idempotency key，并保存请求 hash、状态和结果。相同 key 且 hash 一致时复用已有结果；hash 不一致则拒绝，避免调用语义变化却复用旧结果。”

### 9. 如何设计重试？

“先分类再决定动作。超时、限流、上游 5xx 通常可重试，带退避和次数上限；参数校验、权限、配置错误不能盲目重试；需要用户补充信息的任务进入 `waiting_input`。每次尝试、错误类别、是否 retryable 和最终 disposition 都持久化，方便回放和监控。”

### 10. 用户中途补充信息怎么恢复？

“任务进入 `waiting_input` 时，服务端把允许的字段 schema 和原始请求一起保存。UI 只渲染服务端声明的 text、URL list 或 choice 字段；提交后服务端按保存的原 schema 校验，再把任务重新入队。不能只相信前端传来的 task key 或字段，否则用户可能恢复另一个任务。”

### 11. DAG 为什么比一段串行代码好？

“DAG 把依赖显式化，能并行执行互不依赖的研究任务，也能在数据库里判断哪些任务 ready。它还适合恢复和审计：每个节点有独立状态和 artifact。报告、Persona 和访谈有不同依赖时，DAG 比一个大函数更容易重试局部步骤。”

### 12. 动态 replan 会不会破坏可恢复性？

“不会，因为动态任务不直接写数据库，而是经过 Plan Mutation Service。服务在事务里重新读取 run 状态，校验模板白名单、输入 schema、依赖、额度、报告 gate 和 Skill 版本，再把任务写回同一张 `study_tasks` ledger，并关联 `reasoning_decision_id`。所以动态路径仍然能恢复、回放和审计。”

## C. AI、证据和报告

### 13. 为什么需要 Zod？

“模型输出是非确定的，TypeScript 类型在运行时不存在。Zod 可以在 Provider 返回后验证 JSON 结构、枚举、数组和字段约束。验证失败不会被当成成功结果；Universal Agent 会尝试一次 JSON 修复请求，但修复结果仍需通过同一个 schema。”

### 14. 怎么防止模型胡编来源或结论？

“先从来源连接器得到可保存的 source snapshot，再生成 evidence catalog。报告结论引用 evidence ID 和来源，judge 检查证据覆盖、引用完整性、冲突和结论边界。没有直接行为证据时，报告只能写方向性洞察，并明确下一步需要什么数据。模型不能把搜索摘要或合成访谈包装成已验证事实。”

### 15. 合成 Persona/访谈有什么价值和局限？

“价值是早期探索：快速覆盖假设、生成访谈提纲、发现可能的语言和痛点。局限是它们不是现实样本，容易继承模型偏差，也不能证明真实比例、因果或行为。平台把 synthetic、human、context 等证据状态分开，报告中明确标注；需要验证时要接真实访谈、授权数据或实验。”

### 16. 报告为什么要 judge 和 revise？

“一次生成容易出现结论和证据不匹配、遗漏反例或建议过于泛化。独立 judge 按 answerability、证据覆盖、引用和读者价值给结构化审查；通过就定稿，不通过时把问题转成定向修订约束，而且修订只能使用已有证据目录，不能偷偷新增无来源事实。”

### 17. 来源连接器怎么降级？

“默认先用全网公开网页建立事实基线；明确需要平台信号时，只有启用且合规的官方连接器才走 API。连接器不可用、限流或权限不足，就降级到公开网页、工作区 Context 或用户材料，并在 metadata 和报告里记录采集模式。小红书、抖音等搜索结果不等于站内爬虫数据。”

### 18. Context 和普通 Prompt 拼接有什么区别？

“Context 是有 scope、版本和用途的资产。检索结果保存 retrieval snapshot、命中 chunk 和引用，工具调用可以复现当时拿到的上下文；普通 Prompt 拼接没有版本和审计，也很容易把不相关历史内容带进去。工作 checkpoint 不会自动变成长期 memory，长期记忆需要明确审核和 promotion。”

## D. Agent、SSE 和 Skill

### 19. Agent 可以做哪些动作？

“核心动作是 `call_tool`、`replan`、`ask_user` 和受 Harness 控制的 `finish`。Universal Agent 还可以调用 `persona.list/create`、`interview.create`、`research.create`、`research.run_confirmed` 和 `report.read`。有副作用的动作需要确认，研究没有确认计划时，`research.run_confirmed` 会返回 `plan_not_confirmed`，不会创建运行。”

### 20. 模型动作如何保证安全？

“模型只有建议权。服务端先校验动作 schema，再检查工具目录、workspace 权限、capability grant、参数 schema、预算、依赖和动态额度；拒绝原因作为结构化结果返回下一轮。模型不能直接写 SQL、改变 grant、跳过用户确认，也不能决定报告 gate。”

### 21. SSE 为什么不直接返回完整状态？

“SSE 更适合传输即时增量，完整状态查询可能很大，也可能在断线时丢失。数据库里的 study_events/agent_steps 是权威记录，SSE 发送开始、进度、完成和错误摘要；客户端用 Last-Event-ID 续传，页面刷新后再拉服务端快照。这样连接断开不会改变运行结果。”

### 22. SSE 里为什么不能展示 Chain-of-Thought？

“内部推理可能包含敏感 Prompt、凭据或不稳定的中间内容，也不适合作为审计事实。产品展示的是短 decision summary、工具参数摘要、进度、结果摘要和拒绝原因，既能解释行为，也不会暴露隐藏推理。”

### 23. Skill 和 Tool 的区别？

“Skill 是版本化能力契约，定义输入输出、能力和执行方式；Tool 是一次具体调用。一次 run 会锁定实际 Skill 版本，所以同一运行可以回放。MCP、HTTP 和 Sandbox 都是 executor，必须经过 Skill Gateway 和 workspace grant。”

### 24. 为什么要独立 Sandbox Runner？

“上传 Skill 属于不可信代码，不能在 Next.js 进程里 `eval` 或直接执行。Runner 作为独立服务，每次调用创建临时容器，用非 root、只读文件系统、关闭网络、资源和输出限制，结束后清理。Web 侧只做契约校验和派发，降低 Web 进程、数据库凭据和宿主机被影响的风险。”

### 25. 沙箱为什么默认不能联网？

“共享 Docker/Podman 网络只能做到全开或全关，无法可靠落实每个 Skill 的域名级 egress grant。为了不把‘允许访问某域名’误实现成‘允许访问内网和数据库’，当前所有网络型 Sandbox 请求在派发前拒绝。未来要接入网络，必须放到有代理或防火墙强制出口的专用环境。”

## E. 数据库、安全和工程取舍

### 26. 如何做工作区隔离？

“API 先从 session 得到 viewer 和 workspaceId，领域查询的 where 条件同时带 workspace。公开 URL 使用 public ID，内部关联用数据库 ID；跨工作区资源统一按 not found 返回。数据库层用 Supabase/PostgreSQL 的权限策略和索引配合应用层校验，避免只依赖前端隐藏按钮。”

### 27. 为什么本地还要 PGlite？

“它提供 PostgreSQL 兼容的本地恢复路径，开发和部分 smoke 不需要远程 Supabase。生产仍然可以迁移到 Supabase/PostgreSQL；领域服务尽量依赖 Queryable 接口，而不是把数据库实现写死在页面里。”

### 28. 如何处理 Provider 成本和延迟？

“计划、研究、推理、报告和 judge 可以配置不同 Provider/model；高量研究使用快模型，报告和评审使用更强模型。每次 run 保存 provider、model 和 usage，动态任务、并发、时间和 token budget 都有限制。不能为了省 token 去掉 judge，因为报告质量 gate 是产品契约；应该通过路由、上下文裁剪、缓存和受控重试优化。”

### 29. 你会如何监控这个系统？

“应用侧看 run 完成率、任务失败类别、重试次数、lease 恢复、waiting-input、Provider 延迟和 token 使用；Agent 侧看 action reject、tool/template match、动态任务数和 report gate；Runner 侧看 readiness、active executions、busy/draining/unavailable、执行耗时和错误码。日志和 metrics 都避免放 prompt、token、源文件路径和完整输入。”

### 30. 这个项目目前最大的风险是什么？

“第一是 AI 证据边界，合成内容和公开网页只能支撑方向性判断；第二是长任务对 Provider、队列和存储的依赖，需要持续监控 lease、重试和成本；第三是 Skill 沙箱如果部署错误会扩大风险，所以生产要独立 Linux 主机、rootless runtime、镜像 digest、HTTPS、独立 token 和 readiness gate。当前代码已经把这些边界写进契约，但线上仍要靠部署和运营验证。”

## F. 追问时的反问和收尾

### 面试官问“你会怎么继续优化？”

“我会优先做三件事：一是用真实运行轨迹建立成本、延迟、证据覆盖和人工修订的基线；二是继续把动态任务收敛到版本化 capability template，减少模型自由组合；三是补真实用户研究数据和人工相关性标注，评估 Context 检索和报告结论，而不是只看 JSON 是否成功。”

### 面试官问“你学到了什么？”

“我最大的收获是，Agent 项目的关键是执行治理，不是把 Prompt 写长。模型适合提出假设和下一步，数据库 ledger、权限、预算、恢复和证据契约才负责把系统变成可上线的产品。”
